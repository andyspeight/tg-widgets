Booking Confirmations API

The endpoint the Travelify core platform calls when a booking should get its confirmation email. We check the request, queue it, and send the customer the client's own confirmation email with their booking documents attached. Server‑to‑server only.

POST https://widgets.travelify.io/api/v1/booking-confirmations

The Vercel origin https://tg-widgets.vercel.app/api/v1/booking-confirmations serves the same endpoint if the alias domain is ever unavailable. There are no CORS headers by design: a browser must never call this. It works the same way as the Payment Reminders API.

Authentication

Every request carries a shared secret in a header. It is the same key you already use for the Payment Reminders API, unless we give you a separate one. We never put it in this document.

HeaderValue
X-Api-KeyThe shared secret, sent verbatim. Compared in constant time. A missing or wrong key returns 401 with an empty body and no detail.
Content-Typeapplication/json

Request body

A single JSON object: the three required fields that identify the order, and the address to send to. Everything the email shows comes from the live order, so nothing else is needed and any other field is ignored. A missing or invalid field rejects the whole request with 400 and a per‑field message.

FieldTypeRules
applicationId * integer The client's Travelify App ID. Must be a JSON number (not a string) and a positive integer. Must match a client we already hold; an unknown id returns 400 Unknown applicationId.
orderId * integer The Travelify order id. JSON number, positive integer.
orderKey * string The order's 36‑character GUID (e.g. 3f2504e0-4f89-41d3-9a0c-0305e82c3301). We use it on our server to fetch the live order. It is never shown to the customer.
email optional string The address to send this confirmation to: one plain address, e.g. jo.smith@example.com. Send it every time. If you leave it out we send to the customer email on the order. An invalid address returns 400. We still find the booking by the order's own details, so this can be anyone.

Responses

StatusBodyMeaning
202 { status: "accepted", reference, receivedAtUtc } Queued. Store the reference: it is our handle on this confirmation.
400 { error: "validation_failed", fields: {…} } fields maps each bad field to a message. Also returned for an unknown applicationId. Fix and resend.
401 {} Missing or wrong X-Api-Key.
429 { error: "rate_limited" } Over 2,000 requests in 15 minutes from one IP. Back off and retry.
500 { error: "server_error" } Something went wrong on our side and nothing was queued. Retry the same request.
Treat 202 as success. Retry on 500 and 429: nothing was queued, so a retry cannot send twice. Fix and resend on 400 and 401.

One request, one email

This works exactly like the payment reminders: you decide when a confirmation is wanted, and every accepted request sends one email.

  • Resending is just another request. Send the same applicationId / orderId / orderKey again (after an amendment, say, or for a customer who has lost the email) and a fresh confirmation goes, showing the booking as it stands then.
  • So only repeat what you mean to. We do not remove duplicates. A request that timed out on your side may already have been queued, so check before you send it again, or the customer may get two.
  • Each request is its own record. Every 202 carries its own reference, one per email.
  • Clients also on the Travelgenix webhook. A client connected through the order.complete webhook as well will not get an automatic second email from it for a booking you have already asked us to confirm.

What we send

  • The client's own confirmation email, laid out the way they built it in their My Booking editor, from their own sender name and reply‑to address.
  • The booking documents as a PDF, and the client's ATOL certificate when they hold an ATOL and the booking includes a flight they sold.
  • To the email you send, or to the customer email on the order when you leave it out. We read the live order when we send, so the email always shows the booking as it stands.
  • Usually within a minute. We start work as soon as we have answered you, and a sweep every five minutes picks up anything that did not go first time. A failed send is retried for several hours.

When a request does not send

These are accepted with 202, recorded, and then stopped on our side without an email. None of them needs anything from you.

  • The client has not switched Booking confirmation emails on in their My Booking editor, or has no My Booking widget.
  • The order has no customer email, no departure date or no booking reference. We look the booking up by those, whatever address you ask us to send to.
  • The request is more than 12 hours old by the time we reach it. A confirmation is only useful while it is news.

Current status

The demo app 250 sends, for full end‑to‑end testing. A valid request for a booking on app 250 goes all the way through and emails, so you can see the real confirmation. Real clients are only emailed once they are switched over: the client switches confirmations on and we switch sending on. Until then a valid request for them is still accepted, and the order is read, so you can see the chain work without a customer hearing from us.
