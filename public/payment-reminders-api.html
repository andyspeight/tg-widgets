Payment Reminders API

The endpoint the Travelify core platform calls when an order has a balance due. We validate it, queue it, and send the customer a branded reminder email that links back to the My Booking widget to pay. Server‑to‑server only.

POST https://widgets.travelify.io/api/v1/payment-reminders

The Vercel origin https://tg-widgets.vercel.app/api/v1/payment-reminders serves the same endpoint if the alias domain is ever unavailable. There are no CORS headers by design — a browser must never call this.

Authentication

Every request carries a shared secret in a header. We hold the secret and will share it with you over a secure channel — it is never in this document.

HeaderValue
X-Api-KeyThe shared secret, sent verbatim. Compared in constant time. A missing or wrong key returns 401 with an empty body and no detail.
Content-Typeapplication/json

Request body

A single JSON object. Required fields must all be present and valid, or the whole request is rejected with 400 and a per‑field message.

FieldTypeRules
applicationId * integer The client's Travelify App ID. Must be a JSON number (not a string) and a positive integer. Must match a client we already hold — an unknown id returns 400 Unknown applicationId.
orderId * integer The Travelify order id. JSON number, positive integer.
orderKey * string The order's 36‑character GUID (e.g. 3f2504e0-4f89-41d3-9a0c-0305e82c3301). Case‑insensitive. We use it server‑side to fetch the live order — it is never exposed to the customer's browser.
reminderType * string One of DepositBalance or FinalBalance. Use DepositBalance for a deposit balance or any interim instalment; FinalBalance for the last balance.
amountDue * number The amount due for this stage, in the order currency. Greater than 0, up to 10,000,000. Rounded to 2 decimal places. Advisory only — we recompute the real outstanding from the live order before sending, so a customer who has already paid is never chased.
currency * string Three‑letter ISO 4217 code, e.g. GBP. Case‑insensitive.
dueDate optional string ISO 8601 date YYYY-MM-DD. Optional in general, but required to separate instalments — it is part of the de‑duplication key (see below). Omit it and all instalments for one order collapse into a single reminder.

Optional header — Idempotency-Key: your own key for the notification (printable ASCII, up to 128 chars). When present it overrides the natural de‑dupe key below. Not required; the natural key already makes retries safe.

Responses

StatusBodyMeaning
202 { status: "accepted", reference, receivedAtUtc } Queued. Store the reference (a UUID) — it is our handle on this reminder.
400 { error: "validation_failed", fields: {…} } fields maps each bad field to a message. Also returned for an unknown applicationId. Fix and resend.
401 {} Missing or wrong X-Api-Key.
409 { status: "duplicate", reference } This notification was already accepted. Safe — the reference is the original one. Log it and move on.
429 { error: "rate_limited" } Over 2,000 requests in 15 minutes from one IP. Back off and retry.
500 { error: "server_error" } Transient (recording failed). Retry — the natural de‑dupe key stops a retry ever double‑chasing.

Treat 202 and 409 as success. Retry on 500 and 429. Fix and resend on 400 / 401.

De-duplication & retries

One reminder record represents one balance being chased, not one message per day. The full schedule — the first email plus the follow‑ups the agent configures — lives on that record.

Natural key = applicationId  |  orderKey  |  reminderType  |  dueDate
  • Re‑sending the same balance is safe. If your daily job re‑pushes a balance that is still outstanding, you get 409 with the original reference. It does not start a second chase.
  • A new balance is a new record. A different dueDate, or FinalBalance after an earlier DepositBalance, is treated as a fresh reminder.
  • The window is 60 days. Within that period the same key always resolves to the same reminder.

Instalment plans

For a client whose customers pay in several instalments, send one notification per instalment, on its own due date. Because dueDate is part of the key, each distinct date becomes its own reminder chase.

  • Use reminderType: "DepositBalance" for each interim instalment, and "FinalBalance" for the last one.
  • Set amountDue to that instalment's amount and dueDate to that instalment's date.
  • You do not need to tell us "instalment 2 of 3" — we derive the amount and the instalment position from the live order at send time.

A two‑stage trip (an interim payment then a final balance) is simply one DepositBalance and one FinalBalance, each with its own due date.

Cadence & volume

  • Call roughly daily. Pushing the whole daily batch in one burst from one IP is fine — the rate limit (2,000 / 15 min) is there to stop runaway loops, not to shape normal traffic.
  • Re‑send outstanding balances each day. We re‑check the live order before every email and close the chase the moment the balance is paid, so you never need to send a "cancel".
  • Registration first. Each applicationId must be a client we hold before its notifications are accepted. Travelify's demo app 250 is accepted out of the box for integration testing.

Current status

Email sending is gated off on our side until go‑live. The endpoint already validates, de‑duplicates and queues, so you can integrate and test against the 202 / 409 / 400 responses now. Nothing is emailed to a customer until we flip the switch for a client.
